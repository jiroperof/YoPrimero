1. RESUMEN DE LA ARQUITECTURA
================================================================================
Stack:
  - Lenguaje: Kotlin
  - UI: Jetpack Compose (Material 3)
  - Arquitectura: MVVM
  - Inyección de dependencias: Hilt (elegido por ser el estándar de Google y
    ofrecer generación en compile-time; rápida de configurar con @HiltViewModel)
  - Asincronía: Coroutines + Flow (StateFlow expone el estado de la UI)
  - Navegación: Jetpack Navigation Compose

Patrón general:
  UI (Compose) -> ViewModel (AndroidViewModel) -> Repositorios -> Servicios del sistema

El estado de la UI se expone mediante un StateFlow (DashboardUiState) que el
Dashboard observa con collectAsStateWithLifecycle. Los permisos se leen del
repositorio y se refrescan automáticamente al volver a primer plano (se usa un
LifecycleEventObserver en ON_RESUME), de modo que al regresar de las pantallas
de configuración del sistema el panel se actualiza solo.

3. PERMISOS Y SU FUNCIONAMIENTO
================================================================================
La app requiere permisos "sensibles". Se gestionan desde el panel de permisos
del Dashboard (y se explican en el Onboarding).

AndroidManifest.xml declara:
  - android.permission.INTERNET                     -> conexión normal
  - android.permission.BIND_VPN_SERVICE             -> servicio VPN (Firewall)
  - android.permission.BIND_ACCESSIBILITY_SERVICE   -> servicio de accesibilidad
  - android.permission.SYSTEM_ALERT_WINDOW          -> overlay flotante (HUD)
  - android.permission.KILL_BACKGROUND_PROCESSES    -> RAM Cleaner
  - android.permission.WAKE_LOCK                    -> mantener CPU despierto
  - android.permission.POST_NOTIFICATIONS           -> notificaciones (API 33+)
  - android.permission.FOREGROUND_SERVICE           -> servicios en foreground
  - android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS

Estados que se comprueban (PermissionRepository):
  - OVERLAY:  Settings.canDrawOverlays(context)
  - ACCESSIBILITY: lee Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES
  - VPN:      VpnService.prepare(context) == null
  - NOTIFICATION: POST_NOTIFICATIONS (permiso runtime en API 33+)

Cada fila del panel abre su pantalla de configuración correspondiente:
  - OVERLAY:  ACTION_MANAGE_OVERLAY_PERMISSION con package URI
  - ACCESSIBILITY: ACTION_ACCESSIBILITY_SETTINGS
  - VPN:      VpnService.prepare() (intent de consentimiento del sistema)
  - NOTIFICATION: ACTION_APP_NOTIFICATION_SETTINGS

El permiso de notificaciones runtime (API 33+) se solicita automáticamente al
abrir la app desde MainActivity.onStart().

4. MÓDULOS CORE
================================================================================
-------------------------------------------------------------------------------
4.1 MÓDULO "NETWORK FIREWALL" (FirewallVpnService)
-------------------------------------------------------------------------------
Archivo: service/vpn/FirewallVpnService.kt

Cómo funciona:
  - Extiende VpnService y construye un túnel TUN con VpnService.Builder().
  - Configura los servidores DNS a Cloudflare: addDnsServer("1.1.1.1") y
    addDnsServer("1.0.0.1"). Esto fuerza todas las consultas DNS de las apps
    permitidas a servidores anycast de baja latencia.
  - FIREWALL POR APP: usa builder.addAllowedApplication(...) para cada paquete
    de la lista blanca (Constants.WHITELIST). El sistema operativo bloquea el
    tráfico de red de cualquier app que NO esté en esa lista. Así, las apps de
    reparto/viaje siguen conectadas y el resto queda "aislado".
  - Arranca como servicio foreground con una notificación persistente
    (canal CHANNEL_FIREWALL) para que el sistema no lo mate.
  - Gestiona las acciones ACTION_START / ACTION_STOP vía onStartCommand.
  - Lee el FileDescriptor del túnel en un hilo (startTunReader) listo para
    reenviar paquetes (ver sección 9, "tun2socks").

-------------------------------------------------------------------------------
4.2 MÓDULO "AUTO-CONFIG" (AutoConfigAccessibilityService)
-------------------------------------------------------------------------------
Archivo: service/accessibility/AutoConfigAccessibilityService.kt

Cómo funciona (máquina de estados simple):
  1. Al conectarse (onServiceConnected) abre la pantalla del sistema
     Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS.
  2. Estado WAITING_MODEL: escanea la lista de apps buscando los nombres de la
     whitelist (Yummy, Ridery, Yango) y toca el primero pendiente.
  3. Estado WAITING_DETAIL: dentro de la configuración de una app busca el
     toggle "Permitir"/"Don't allow" y lo activa (ACTION_SET_CHECKED),
     luego retrocede a la lista.
  4. Repite hasta agotar la whitelist.

Robustez frente a variaciones de UI:
  - Busca nodos por texto visible y por contentDescription.
  - Sube por los padres (hasta 6 niveles) buscando un nodo clickeable y visible.
  - Detecta switches por isCheckable o por className que contenga "Switch".
  - Reconoce textos en varios idiomas (Permitir / Allow / Don't allow...).

Config del servicio: res/xml/accessibility_service_config.xml (flags y type).

-------------------------------------------------------------------------------
4.3 MÓDULO "HUD & WAKELOCK" (HudOverlayService)
-------------------------------------------------------------------------------
Archivo: service/overlay/HudOverlayService.kt

Cómo funciona:
  - Crea una ventana flotante (System Alert Window / TYPE_APPLICATION_OVERLAY)
    que muestra "DriverPing · <ping> ms" en la esquina superior.
  - El overlay es ARRASTRABLE (se implementa el manejo de eventos táctiles
    con umbral para distinguir tap de arrastre).
  - MEDICIÓN DE PING: lanza una consulta DNS (UDP) a 1.1.1.1:53 con un
    DatagramSocket y cronometra la ida+vuelta. Se usa DNS UDP en vez de ICMP
    nativo porque el ping ICMP requiere CAP_NET_RAW (root). Esto es la forma
    fiable de medir latencia sin privilegios.
  - Actualiza el ping cada Constants.PING_INTERVAL_MS (3 s) en un coroutine IO
    y publica el resultado en el hilo principal con un Handler.
  - WAKELOCK: adquiere un PartialWakeLock (util/WakeLockHelper) al iniciar
    onCrate y lo libera en onDestroy. Evita que la pantalla/CPU entre en Doze
    mientras el Modo Trabajo está activo (además el overlay usa
    FLAG_KEEP_SCREEN_ON).
  - Arranca como servicio foreground con notificación (canal CHANNEL_HUD).

-------------------------------------------------------------------------------
4.4 MÓDULO "RAM CLEANER" (util/RamCleaner.kt)
-------------------------------------------------------------------------------
Cómo funciona:
  - cleanAllBackgroundExcept(context, whitelist): obtiene la lista de procesos
    en ejecución (ActivityManager.getRunningAppProcesses) y mata los procesos
    en segundo plano con killBackgroundProcesses(...) para todas las apps
    EXCEPTO la whitelist, apps esenciales del sistema (systemui, settings,
    la propia app) y paquetes com.android.*.
  - killBackgroundProcesses(context, packages): mata un conjunto concreto.
  - Se invoca al activar el Modo Trabajo desde el ViewModel (en segundo plano
    con Dispatchers.IO) y se informa de cuántos procesos se terminaron.

También incluye WakeLockHelper (partial wake lock gestionado globalmente).

5. FLUJO DE PERMISOS (ONBOARDING + DASHBOARD)
================================================================================
FLUJO DE LA APP:
  1. MainActivity inyecta SettingsRepository (Hilt).
  2. AppNavHost decide la pantalla inicial:
       - Si el onboarding NO se ha completado -> OnboardingScreen.
       - Si ya se completó -> DashboardScreen.
  3. OnboardingScreen es un carrusel de 4 pasadas que EXPLICA cada permiso
     antes de pedirlo:
       1) Bienvenida       2) Firewall VPN   3) HUD Flotante   4) Accesibilidad+
  4. Al terminar marca onboarding_done=true (SharedPreferences) y navega al
     Dashboard eliminando el onboarding del back stack.
  5. DashboardScreen:
       - Panel de permisos con barra de progreso "n/x concedidos".
       - Tocar una fila abre la configuración del permiso correspondiente.
       - Al volver, los permisos se refrescan automáticamente (ON_RESUME).
       - Botón grande "Activar/Desactivar Modo Trabajo" (deshabilitado hasta
         tener todos los permisos; con spinner mientras "prepara entorno").
       - Notifica resultados con Snackbar (p. ej. núm. de procesos limpiados).

DASHBOARD VIEWMODEL (DashboardViewModel):
  - Expone DashboardUiState (workModeActive, permissions, allPermissionsGranted,
    progress, message, ramProcessesKilled).
  - startWorkMode() máquina de pasos:
      1) Limpia RAM en IO (RamCleaner).
      2) Comprueba VpnService.prepare(context).
      3) Arranca HudOverlayService (startForegroundService).
      4) Arranca FirewallVpnService si la VPN está preparada.
      5) Marca workModeActive en memoria y persiste en SharedPreferences.
  - stopWorkMode(): detiene los dos servicios y limpia el estado.
  - El estado del Modo Trabajo se restaure al iniciar (init) leyendo la prefs.

8. CÓMO COMPILAR Y EJECUTAR
================================================================================
Este entorno NO tiene Android SDK ni Gradle instalados, así que no se pudo
compilar aquí. Para compilar localmente:

  1. Abrir el proyecto con Android Studio (Iguana o superior).
  2. Dejar que Gradle sincronice y descargue dependencias (esto generará el
     gradle wrapper automáticamente: gradlew, gradle/wrapper/*).
  3. Seleccionar un dispositivo/emulador y pulsar Run.
     - Requiere minSdk 24 (Android 7.0) y targetSdk/compileSdk 34.
     - Java 17 (configurado en compileOptions/kotlinOptions).

Versiones (en app/build.gradle.kts):
  - compileSdk / targetSdk: 34, minSdk: 24
  - Kotlin 1.9.22, AGP 8.2.2, KSP 1.9.22-1.0.17, Hilt 2.50
  - Compose BOM 2024.02.01, Navigation Compose 2.7.7, Lifecycle 2.7.0

Para usar en un teléfono real:
  - Activar "Orígenes desconocidos" / instalar el APK de debug.
  - Conceder TODOS los permisos desde el Dashboard y tocar "Activar Modo Trabajo".

9. LIMITACIONES TÉCNICAS IMPORTANTES Y SIGUIENTES PASOS
================================================================================
PUNTO CRÍTICO 1 - Reenvío de paquetes (tun2socks):
  El VpnService bloquea por app (addAllowedApplication) y fuerza el DNS, que es
  el núcleo del firewall y de la reducción de latencia. El bloqueo de apps NO
  permitidas es real (el sistema no les da salida a Internet).

  PERO: una vez establecido el túnel, Android espera que la app que controla la
  VPN LEA cada paquete del FileDescriptor y lo reenvíe por un socket real, y que
  las RESPUESTAS vuelvan al túnel. Esto se llama "client tun" o "tun2socks".
  Sin ese reenvío, las apps permitidas quedan conectadas al túnel pero no tienen
  salida de datos (aunque el ahorro de bloqueo de las demás sigue activo).

  En este MVP se configura el firewall+DNS correctamente y se deja el bucle de
  lectura del FD (startTunReader) con el hook documentado en el TODO del código.
  Para producción hay dos opciones:
    a) Integrar una librería nativa tun2socks (p. ej. p2p/iop or socat no);
       la opción estándar es usar librerías como "libtun2socks" o el cliente
       del proyecto "Shadowsocks-VPN" para Android (go w/ ProxyProtocol).
    b) Implementar reenvío UDP/DNS solo con DatagramSocket protegidos, leyendo
       del tun y devolviendo cada paquete de respuesta al tun (más largo pero
       sin dependencias nativas). En la primera versión se intentó esto pero se
       retiró por no devolver respuestas correctamente.

PUNTO CRÍTICO 2 - Navegación del AccessibilityService por marcas:
  La UI de "Optimización de batería" varía según el fabricante (MIUI, EMUI,
  OneUI, RealmeUI...). El servicio hace un barrido por textos genéricos y
  subiendo por los padres buscando nodos clickeables, pero para marcas muy
  personalizadas puede requerir ajustar los textos/IDs. El string
  "accessibility_description" también debe estar presente en la Play Store.

PUNTO CRÍTICO 3 - Toque con respecto a la Play Store:
  Una app que abusa de Accessibility, VPN y Overlay puede ser rechazada por
  Google (políticas de "masquerading" y "unwanted software"). Para distribución
  real:
    - Justificar el uso de AccessibilityService con el campo description.
    - Justificar el uso de VpnService/Overlay en la consola de Play.
    - Esta app está pensada para uso personal/sideloading o un listado
      empresarial gestionado (looka y privado).

PUNTO CRÍTICO 4 - Permiso de "Ignorar optimización de batería":
  REQUEST_IGNORE_BATTERY_OPTIMIZATIONS está declarado. El flujo actual abre
  ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS vía Accessibility. Se puede
  además añadir un botón directo que abra ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS
  para la propia app.

Próximos pasos sugeridos (orden de prioridad):
  1. Integrar tun2socks para dar salida completa a las apps de la whitelist.
  2. Añadir Settings de usuario (editar la whitelist desde la UI).
  3. Añadir botón directo "Ignorar optimización de batería" de la propia app.
  4. Guardar y mostrar el histórico de pings en DataStore/Room.
  5. Widget o acceso rápido al Modo Trabajo.
  6. Pruebas unitarias (ViewModel, repositorios) y tests de instrumentación.

10. NOTAS DE SEGURIDAD Y CUMPLIMIENTO
================================================================================
  - La whitelist vive en util/Constants.kt (objeto Constants -> WHITELIST).
    Es la ÚNICA fuente de verdad; si cambian los paquetes de las apps de las
    empresas, se actualiza ahí.
  - No se almacenan datos personales ni credenciales.
  - La app no accede ni exporta el tráfico de las apps; solo reenvía el de la
    whitelist y bloquea el del resto a nivel de sistema.
  - Los WakeLock y servicios foreground se liberan/detienen correctamente al
    desactivar el Modo Trabajo, evitando drenaje de batería.
  - NOTA LEGAL/ÉTICA: esta herramienta modifica el comportamiento de red del
    dispositivo de forma local. El usuario final debe dar su consentimiento
    explícito a los permisos (por eso el onboarding). Usar automatización de
    accesibilidad para alterar los ajustes del sistema debe hacerse de forma
    transparente y solo sobre los ajustes que el usuario autoriza.
